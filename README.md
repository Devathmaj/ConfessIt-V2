## CONFESSIT README

### Compose environment files

Keep infrastructure and deployment variables in the root `.env`, and backend
application settings in `backend/.env`. The game scheduler uses the restricted
`backend/.scheduler.env`; create it from `backend/.scheduler.env.example` and
set the listed database, signing, and cleanup settings to match `backend/.env`.
Compose builds the scheduler's Redis URL from the root infrastructure password.
The scheduler file contains no chat encryption key or unrelated backend service
credentials.

### LLM providers (story generation for Plot Twist and Case Closed)

Blueprints and story packages for both games are generated by one shared,
provider-configurable client (`backend/app/services/llm_client.py`); runtime
gameplay never calls a model. Switching providers is environment
configuration, never a code change:

- `LLM_PROVIDER`: `groq` (default) or `foundry`. Legacy spellings `openai`
  (the same path as `foundry`) and `auto` (Groq when the base URL names it)
  keep old deployments working. Anything else refuses to boot.
- `LLM_MODEL`: Groq model id (e.g. `openai/gpt-oss-120b`,
  `qwen/qwen3.8-27b`) or the Microsoft Foundry *deployment name* (e.g.
  `gpt-5-mini` -- the deployment, not necessarily the underlying model id).
- `LLM_BASE_URL`: `https://api.groq.com/openai/v1` (Groq) or the
  OpenAI-compatible Foundry v1 endpoint
  `https://<resource>.services.ai.azure.com/openai/v1`. A trailing
  `/responses` or `/chat/completions` copied from the portal is normalised
  away, so the request path is never doubled.
- `LLM_API_KEY`: the provider API key. Never logged, never committed.

`foundry` is reached through the official OpenAI Python SDK
(`OpenAI(base_url=..., api_key=...)`) with the same prompts, strict JSON
Schema request, JSON-object fallback and local validation as the Groq path.
A missing endpoint/key, an unsupported provider, or a provider failure is a
clear error: requests are never silently rerouted to the other provider.
Example foundry configuration (placeholders, keep secrets out of git):

```
LLM_PROVIDER="foundry"
LLM_MODEL="gpt-5-mini"
LLM_BASE_URL="https://<resource>.services.ai.azure.com/openai/v1"
LLM_API_KEY="<key>"
```

### Automated sessions (Plot Twist and Case Closed)

Both AI games generate and publish their sessions unattended on the existing
00:01 UTC scheduler: no admin runs blueprint -> approve -> package -> publish
any more, and runtime gameplay still never calls a model.

- The boundary tick is a checkpoint, not a generation deadline. For each AI
  game the scheduler finalizes the expired session the way it always did
  (Case Closed reveals the culprit, scores everyone and notifies both
  partners), then enqueues exactly one generation cycle per
  `(game_id, cycle_start_date)` and returns. The playable session opens only
  after the worker publishes a validated package, which may happen minutes
  after the tick.
- Queue and worker: `game_generation_jobs` (status
  `queued | running | retry_wait | published | failed | cancelled`, unique on
  `(game_id, cycle_start_date)`) is claimed with `FOR UPDATE SKIP LOCKED` plus
  a stale-running reclaim, so duplicate delivery and a crashed worker are both
  safe. The API process runs `GenerationWorker`
  (`backend/app/services/ai_game_automation.py`) on
  `AI_GENERATION_WORKER_ENABLED` (default true; `false` parks the queue and
  lets a run-resets pass or a test drive `process_due_jobs` directly).
- Serialization: the two games never generate concurrently, on one process or
  many -- every claim runs inside one shared Postgres advisory lock
  (`AI_GENERATION_LOCK_KEY`, a bounded wait of `AI_GENERATION_LOCK_WAIT_SECONDS`,
  default 120) rather than any in-memory flag, so multiple workers and
  replicas queue behind each other and failures always release it.
- Publication is one transaction under the game's lifecycle lock: it re-checks
  the job, the game's hidden switch and any active revocation, re-validates the
  stored package, ends the live session (finalizing Case Closed first), opens
  the new session for `period_for_start(today, cadence)`, snapshots the league
  opportunity and marks the job published. Re-running it converges on the same
  outcome -- no duplicate sessions.
- Failures retry with backoff (`AI_GENERATION_RETRY_BACKOFF_SECONDS`) up to
  `AI_GENERATION_MAX_ATTEMPTS` (3), then park as `failed` with the provider
  error recorded on the job and shown in the console; the next cycle starts
  clean. A failure never blocks the other game or later cycles.
- Difficulty is stored per game on `game_configs.difficulty`
  (`easy | medium | hard`, null-ready for every other game) and snapshotted
  into the job when the cycle is enqueued, so a mid-flight change applies from
  the next session, never to content already being generated. The frequency
  picker is the existing reset cadence
  (`daily | every_2_days | every_3_days | every_5_days | weekly`).
- Revoke ("Revoke session" in the console) is distinct from hide and disable:
  it ends the live session -- or cancels an in-flight generation -- immediately,
  opens no replacement, and records an audit marker
  (`game_session_revocations`) that suppresses the same cycle. The next session
  appears only at the next eligible scheduled cycle, repeated revokes are safe
  no-ops, and a stale job can never publish after a revoke or a hide.
- Admin console: each game page offers difficulty, frequency
  (enable/hide/revoke carried by the shared controls), an inspector for the
  currently published content (scenes/choices/endings for Plot Twist,
  opening/suspects/leads/solution for Case Closed), the latest generation
  status or last error on an empty screen, and a backend-paginated session
  history (`GET /admin/{plot-twist|case-closed}/sessions?skip=&limit=`, same
  envelope as every other games history read). The old blueprint/package
  routes remain as the pipeline's internal recovery surface but are absent
  from the UI. `GET /admin/{game}/session` answers
  `{session, generation}` -- a 200 with `session: null` rather than a 404.
- Schema converges at boot like the rest of the repo (no Alembic):
  `game_generation_jobs`, `game_session_revocations` and
  `game_configs.difficulty` are created by `PostgresClient.initialize()`.
- Tests: `backend/tests/test_ai_game_automation.py` (25 tests: one cycle per
  boundary, unattended lifecycle for both games, cross-worker serialization
  with a contended advisory lock, provider failure/retry/park, stale-job
  reclaim, revoke during generation, hide mid-pipeline, difficulty snapshots,
  paginated admin reads). Run:
  `docker compose exec backend python -m pytest tests/test_ai_game_automation.py -q`.
  Frontend: `npm test -- --run tests/adminPlotTwist.test.tsx tests/adminCaseClosed.test.tsx`.

### Hybrid search (keyword + semantic, confessions, pgvector + Azure text-embedding-3-small)

One search box runs both signals: keyword matches first, similar-in-meaning
below, deduped so a row never appears twice.

- Model: `text-embedding-3-small`, dimensions: `1536`, column: `vector(1536)`
  (`confession_embeddings.embedding`). Query and confession embeddings always
  use the same model/dimensions; vectors are validated as exactly 1536 finite
  numbers and never truncated, padded, or reshaped.
- Embedding input is the confession's public text only (body + optional public
  recipient name). Comments, identities, reports, moderation notes, and counts
  are never embedded. Exactly one embedding per confession, written once on
  creation; no edit regeneration, no backfill. Hard delete cascades;
  soft-removed (`removed_at`) rows are excluded in SQL on the public path and
  included-and-flagged on the staff path.
- Azure route implemented in `backend/app/services/embedding_service.py`
  (Foundry v1, no api-version):
  `POST {EMBEDDING_ENDPOINT}/openai/v1/embeddings`
  with `api-key` header and `{"model": "<deployment>", "input": [...], "dimensions": 1536}`.
  `model` is `EMBEDDING_DEPLOYMENT` when set, else `EMBEDDING_MODEL`
  (the Azure deployment name, which often equals `text-embedding-3-small`).
- Runtime configuration (environment, never committed):
  `EMBEDDING_ENDPOINT="https://confessit-model.services.ai.azure.com"`,
  `EMBEDDING_API_KEY`, `EMBEDDING_MODEL="text-embedding-3-small"`,
  `EMBEDDING_DIMENSIONS="1536"`, `EMBEDDING_SEARCH_ENABLED="true"`,
  plus hybrid knobs `EMBEDDING_MIN_SIMILARITY="0.30"` (cosine-similarity floor;
  no universal threshold, tune per corpus), `EMBEDDING_SEMANTIC_TOP_K="10"`,
  `EMBEDDING_MIN_QUERY_CHARS="3"` (shorter queries skip the provider),
  `EMBEDDING_SEARCH_RATE_LIMIT_PER_MINUTE="30"` (public bucket) and
  `EMBEDDING_ADMIN_SEARCH_RATE_LIMIT_PER_MINUTE="60"` (staff bucket, `0` disables).
- PostgreSQL requirement: the `pgvector/pgvector:pg16` image (see
  `docker-compose.yml` / `docker-compose.prod.yml` and `postgres-init.sql`
  `CREATE EXTENSION IF NOT EXISTS vector`). Keyword search reuses the existing
  pg_trgm GIN indexes on `confessions(body)` / `confessions(recipient_name)`
  (`ix_trgm_confessions_body`, `ix_trgm_confessions_recipient_name`, created at
  boot by `PostgresClient.apply_trgm_indexes`) -- no new migration; the repo
  has no Alembic, schema converges via `PostgresClient.initialize()`. The app
  also creates the vector extension at boot and a best-effort HNSW cosine
  index; exact search remains correct without the index on a small corpus.
  Managed hosts need superuser/`rds_superuser` or a pre-installed extension.
- Database init: `PostgresClient.initialize()` creates `confession_embeddings`
  (FK `confessions.id` CASCADE, UNIQUE `confession_id`) via the existing
  `create_all` + additive-DDL mechanism. A disposable dev database may be
  recreated; no worker is required (synchronous generation with graceful
  degradation when Azure is unavailable).
- Search APIs (both return `{keyword: {items, total}, semantic: {items, status}}`
  with `status` in `ok | disabled | unavailable | rate_limited | skipped_short`;
  blank/over-long queries are still 422):
  `POST /confessions/search` with `{"query": "...", "limit": 10}` (public shape,
  removed excluded, never matches identity).
  Example: `curl -X POST $API/confessions/search -H "Authorization: Bearer <jwt>"`
  `-H "Content-Type: application/json" -d '{"query":"homesick night thoughts","limit":5}'`.
  `GET /admin/confessions/search?q=...&filter=all&sort=recent&skip=0&limit=10`
  (staff shape, removed included-and-flagged, sender-aware lexical kept).
  Keyword ranks by trigram similarity then recency; semantic ranks by pgvector
  cosine distance (`<=>`) ascending (`1 - distance` is cosine similarity, not a
  probability). Shared pipeline lives in
  `backend/app/services/semantic_candidates.py` (embed + vector query +
  threshold + dedupe); per-bucket budgets in
  `backend/app/services/semantic_rate_limit.py`.
- Frontend: `ConfessionsPage` "Search confessions" (debounced, stale-cancelling)
  renders "Keyword matches" then "Similar in meaning" with a non-blocking notice
  when `semantic.status` is not `ok`; `ConfessionsAdmin` review search renders
  the same two sections with removed flags and admin columns.
  `GET /admin/confessions/reports` is unchanged.
- Tests: `backend/tests/test_hybrid_search.py` (10 tests: dedupe, semantic-only,
  removed visibility, identity rules, degradation, buckets, threshold, short
  queries, 422s, admin filter/sort) plus `backend/tests/test_semantic_search.py`
  (24 tests, endpoint assertions updated to the hybrid shape). Provider calls are
  mocked; vector ordering/threshold run against real pgvector. Run:
  `docker compose exec backend python -m pytest tests/test_hybrid_search.py tests/test_semantic_search.py -v`.
  Frontend: `npm test -- --run tests/confessionsHybridSearch.test.tsx tests/confessionsAdminPaging.test.tsx`.
